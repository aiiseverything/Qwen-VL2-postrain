# 踩坑清单：症状 → 原因 → 解法

> 组织方式：每条给出**症状**（你会看到什么）、**原因**（为什么）、**解法**（怎么办）。
> 标 🔴 的是**静默失败** —— 不报错、不崩溃，但结果全错，最危险。
> 标 ⭐ 的是本次实际踩到并已修复的坑。

## A. 数据与下载

### ⭐🔴 A1. 数据集下载完只有 JSON，没有图像/视频

- **症状**：`LLaVA-Instruct-150K` / `ShareGPT4V` / `VideoInstruct-100K` 下完只有几个
  `.json`，`du -sh` 只有几百 MB 到 1 GB。
- **原因**：这些仓库**只托管标注**。图像/视频本体在别处：
  - LLaVA / ShareGPT4V 的图像来自 **COCO / GQA / TextVQA / VisualGenome / SAM** 等上游；
  - VideoInstruct 的视频来自 **YouTube**（`video_id` 形如 `v_k_ZXmr8pmrs`，`v_` 后是 YouTube ID）。
- **解法**：见 `scripts/download/01b_images.sh`。先统计标注里的 `image` 前缀分布，
  再逐前缀确定上游来源；`ocr_vqa` 前缀上游约 250 GB，建议直接剔除。
- **检查**：`python3 -c "import json,collections;d=json.load(open('llava_v1_5_mix665k.json'));print(collections.Counter(x['image'].split('/')[0] for x in d if x.get('image')))"`

### ⭐ A2. 学术站点下载慢到不可用（0.03–0.05 MB/s）

- **症状**：`images.cocodataset.org` / `downloads.cs.stanford.edu` 下载 20 GB 显示
  剩余时间 **几十小时到几天**。
- **原因**：这些站点在国内网络环境下国际出口带宽极差。
- **解法**：改用 HF 镜像，实测提速 **83–113 倍**：

  | 原始源 | 速率 | HF 镜像 | 速率 |
  |---|---|---|---|
  | `images.cocodataset.org` | 0.05 MB/s | `pcuenq/coco-2017-mirror` | 4.15 MB/s |
  | `downloads.cs.stanford.edu` | 0.03 MB/s | `Feeky929/GQA-images` | 3.40 MB/s |

- **通用做法**：在 HF 上 `search=<数据集名>` 找镜像，**下载前先测 30 MB 区间的实际速率**再决定源。

### ⭐🔴 A3. `hf download` 进程活着但完全不传数据（0.00 MB/s）

- **症状**：`hf download` 进程 `ps` 可见、状态 `Sl`，但 `.incomplete` 文件字节数长时间不变；
  同期其它下载正常。**不报错、不超时、不退出。**
- **原因**：`hf_xet`（HuggingFace 的 Xet 传输后端）在部分网络下会**静默卡死**。
- **解法**：卸载 `hf_xet`，让 `huggingface_hub` 回退到普通 HTTP：
  ```bash
  uv pip uninstall hf_xet
  ```
  > ⚠️ 实测 `HF_HUB_DISABLE_XET=1` 在 `huggingface_hub 1.32.0` 下**不生效**，
  > 必须直接卸载包。
- **附带影响**：卸载后重启下载会**新建一个 `.incomplete`**（hash 后缀不同），
  不会续传旧的那份。旧的孤儿文件要手动删，否则白占空间。

### ⭐ A4. 跨源续传产生静默损坏的文件

- **症状**：把下载从源 A 换到源 B 后 `curl -C -` 从旧 partial 继续，
  下载**正常完成且不报错**，但几小时后解压时才发现 `unzip: bad CRC`。
- **原因**：`curl -C -` 只按**字节偏移**续传，不校验前序字节是否来自同一个文件。
  两个源的同名文件内容不同时，结果是拼接产物。
- **解法**：换源时**删掉 partial 重下**（几秒代价 vs 几小时代价）；
  归档下载完成后、解压前加一道完整性校验：
  ```bash
  unzip -tq archive.zip && echo OK || echo "损坏，需重下"
  ```
- **教训**：**「下载成功」不等于「文件正确」**。

### ⭐🔴 A5. `pkill -f "<脚本名>"` 把自己杀掉了

- **症状**：执行 `pkill -f "01b_images.sh"`，命令以 **exit code 144** 结束、无输出，
  后续清理指令**全部没执行**。
- **原因**：`pkill -f` 匹配**完整命令行**，而执行该命令的 shell 自身命令行里
  就含 `01b_images.sh` 这个字符串 —— 它把自己也匹配并杀了。
- **解法**：**按 PID 精确 kill**：
  ```bash
  ps -eo pid,args | grep '[0]1b_images'      # 注意 [0] 技巧避免匹配自身
  kill -9 <PID>
  ```
  项目里已提供 `record_pid` / `stop_by_pidfile`（见 `scripts/download/_common.sh`）。

### ⭐ A6. `image` 字段缺失 ≠ 数据损坏

- **症状**：LLaVA-665K 有 40,688 条没有 `image` 键。
- **原因**：这些是**纯文本 ShareGPT 对话**（编程问答、常识问答等），
  本就不该有图。键集合是 `('conversations','id','model')`。
- **解法**：抽取时显式剔除并记录数量，不要当作错误，也不要混进 VLM 的 SFT 数据。

### ⭐ A7. 两个「不同」数据集其实高度重叠

- **症状**：按配方分别从 LLaVA-665K 取 235K、从 ShareGPT4V 取 65K，
  以为得到 30 万条多样数据。
- **原因**：`ShareGPT4V` 的 `mix665k` 是**在 LLaVA-665K 基础上改写**的，
  两者 coco/vg/gqa/textvqa 的图像高度重合 —— 实际有大量**同图重复**。
- **解法**：用 ShareGPT4V 的 **`cap100k`**（GPT-4V 生成的 caption，内容独立）
  而非 `mix665k`；或做图像级去重后再合并。
- **通用做法**：合并多个来源前，**先做图像/文本指纹去重**，并统计重叠率。

## B. RLVR / 奖励函数

### ⭐🔴 B1. 答案列名不一致 → 奖励恒为 0，训练"正常"跑完却啥也没学到

- **症状**：GRPO 跑满 200 step，loss 曲线看着正常，但 reward 始终是 0，
  模型输出没有任何改善。**没有任何报错。**
- **原因**：各数据集的答案列名和格式都不同：

  | 数据集 | 列名 | 值样例 |
  |---|---|---|
  | `hiyouga/geometry3k` | `answer` | `3` |
  | `leonardPKU/GEOQA_R1V_Train_8K` | **`solution`** | `<answer> 145° </answer>` |
  | `FanqingM/MMK12` | `answer` | 裸答案 |

  按 `answer` 取 geoqa 会拿到**空标签**；用字符串相等比 `145°` 与
  `<answer> 145° </answer>` 则**永不相等**。
- **解法**：奖励函数先**剥离 `<answer>/<solution>/<think>` 标签**再做比较
  （见 `configs/reward_geo.py`），并且**上机第一步先跑奖励函数的单元测试**，
  用真实数据抽样人工核对几条 reward 是否合理。
- **自查**：训练开始后**立刻看 reward 的均值和方差**。若恒为 0 或方差为 0，
  停下来查数据，不要等 200 step 跑完。

### 🔴 B2. 在 2B 模型上强制 CoT 格式奖励会掉分

- **症状**：加了 `<think></think>` 格式奖励后，准确率反而比不加更低。
- **原因**：小模型没有足够的指令遵循能力来同时满足「格式」和「答对」，
  格式奖励会把优化方向带偏（R1-V 在 Qwen2-VL-2B 上的自述）。
- **解法**：格式奖励**默认关闭**（`reward_geo.py` 的 `format_reward=0.0`），
  作为一次消融实验单独验证，不要默认打开。

## C. 训练

### C1. 显存 OOM，且是「视觉 token 数量」而非 batch size 引起的

- **症状**：`per_device_train_batch_size` 调小仍然 OOM；换一张图就炸。
- **原因**：Qwen2-VL 用 **Naive Dynamic Resolution** —— 图像被切成
  28×28 的 patch，**分辨率越高视觉 token 越多**。一张 1024×1024 的图
  约 1300+ token，是 512×512（约 334 token）的 4 倍。
  `image_max_pixels` 不设限时，长宽比极端的图会产生巨量 token。
- **解法**：**必须显式设置 `image_max_pixels`**（本项目用 262144 = 512×512）。
  显存不够时优先降这个值，而不是降 batch size。
- **推导**：视觉 token 数 ≈ `(H/28) × (W/28)`。

### C2. DPO 学习率设成 SFT 量级 → 模型崩溃

- **症状**：DPO 训练后模型输出重复、乱码或完全失去指令遵循能力。
- **原因**：DPO 的梯度尺度与 SFT 不同，**对学习率极其敏感**。
  用 SFT 的 1e-5 会让 policy 相对 reference 偏移过大，直接训崩。
- **解法**：DPO lr 用 **5e-7**（比 SFT 低 20 倍），并**先跑几十 step 看
  `rewards/accuracies` 是否在 0.5–0.8 之间**。若迅速冲到 1.0 说明 lr 太大。

### C3. DeepSpeed 配置与 batch size 不匹配

- **症状**：`AssertionError: train_batch_size does not match`。
- **原因**：`ds_zero2.json` 里 `train_batch_size: "auto"` 需要框架正确推导；
  手写固定值时容易与 `per_device × grad_accum × N卡` 对不上。
- **解法**：保持 `"auto"`，让 LLaMA-Factory 自己填。

### C4. 多卡训练卡住 / NCCL 超时

- **排查顺序**（从最常见开始）：
  1. **某张卡被别的进程占了** → `nvidia-smi` 看显存；本项目机器上就常年有别的任务。
  2. **端口冲突** → 换 `MASTER_PORT`。
  3. **无 IB 却尝试走 IB** → `export NCCL_IB_DISABLE=1`。
  4. **大图像 batch 导致单步过长** → `export NCCL_TIMEOUT` / `ddp_timeout: 180000000`。
  5. **网络接口选错** → 指定 `NCCL_SOCKET_IFNAME`。
  6. 打开 `NCCL_DEBUG=INFO` 看卡在哪一步。

### C5. checkpoint 保存与恢复的坑

- **症状**：`--resume_from_checkpoint` 报找不到文件，或恢复了但 step 归零。
- **原因**：ZeRO-2 的 checkpoint 是分片的，路径下还有 `global_step*` 子目录。
- **解法**：直接把 `checkpoint-<N>` 目录传给 `--resume_from_checkpoint`；
  本项目 `launch_4xl40.sh` 已自动探测最新 checkpoint。
- ⚠️ **2026-09-27 更正**：原来这里写「`save_steps` 不要设太小，否则保存会成为**瓶颈**」——
  这个说法**严重低估了**。实测每次保存会永久吃掉 ~25 GB host 内存且不归还，
  在 64 GiB 容器上限下**第二次保存必死**。详见 **C6 / C7**。

### C6. 🔴 host 内存 OOM：**不是显存**，且日志里只留一行 SIGKILL

- **症状**：训练中途进程消失，日志只有 `exitcode: -9 (SIGKILL)`；
  **完全看不到 CUDA OOM**，显存还有富余。
- **原因**：**容器 cgroup 内存上限（本项目 64 GiB）远小于宿主机内存（503 GB）**。
  `free -g` 看到的是宿主机，会把人带偏。判定必须看：
  ```bash
  cat /sys/fs/cgroup/memory.max      # 真正的天花板
  cat /sys/fs/cgroup/memory.events   # oom_kill / max 计数
  ```
  放大器是 **`dataloader_num_workers` × 卡数**：worker fork 后 COW 逐步私有化，
  匿名内存单调上涨（本项目 worker=8 时 56 个进程，涨速 ~95–180 MB/s）。
- **解法**：`dataloader_num_workers: 1`（先治漂移）；**调 batch size 完全没用** ——
  那是显存侧的旋钮。
- **不要**用短跑验证：必须**至少触发两次同类事件**才能暴露累积效应（见 P38）。

### C7. 🔴 每次存 checkpoint 永久吃掉 ~25 GB host 内存，且**不归还**

- **症状**：能跑完第一个 `save_steps`，第二次保存必死；或者保存后内存就一直高着。
- **原因**：写文件前必须在主机内存里凑出要写的字节（**GPU→CPU 拷贝 + 序列化缓冲**），
  ZeRO-2 存一次 = 23 GB optimizer 分片 + 4.6 GB 权重；实测 **7 个 rank 各自物化一份**。
  `MALLOC_ARENA_MAX` / `MALLOC_TRIM_THRESHOLD_` / `MALLOC_MMAP_THRESHOLD_` **无效**（不是 glibc 碎片）；
  `save_only_model: true` **也无效**（照样 +20 GB）。保存后这份内存**不还给操作系统**。
- **解法（64 GiB 上限下的取舍）**：`save_steps` 设成大于总步数 ⇒ **不存周期 checkpoint**。
  收尾时 LLaMA-Factory 仍会无条件 `trainer.save_model()`
  （`train/sft/workflow.py:122`），模型照样产出，DPO 不受影响。
  **代价：中途崩了没有任何存档可续。**
- **更优解**：把容器上限调到 128 GiB，即可用回正常 `save_steps`。

## D. 评测

### 🔴 D1. 分数不可跨工具比较

- **症状**：用官方脚本跑出的 MME 分数，和别的论文里同一模型的分数对不上。
- **原因**：prompt 模板、答案抽取方式（正则 vs GPT）、抽帧策略不同，
  会让**同一个模型**的分数差好几个点。
- **解法**：**四个模型 × 三个 benchmark 全部用同一个工具链**（本项目统一用 VLMEvalKit）。

### 🔴 D2. MathVista 用规则抽取判分 ≠ 论文分数

- **症状**：MathVista 分数明显低于论文报的。
- **原因**：官方协议用 **GPT 抽取答案**并判分；无 API key 时只能用规则抽取，
  对复杂输出的抽取准确率差很多。
- **解法**：没有 key 就在报告中**明确标注「非官方判分，不可与论文直接比较」**。

### ⭐ D3. 训练集与评测集重叠 → 分数虚高

- **症状**：模型在某个 benchmark 上分数异常高，但实际能力没提升。
- **原因**：SFT 数据里混进了评测集的图像（COCO/TextVQA 等与 MME/MathVista 有交集）。
- **解法**：训练前做**图像级去污染**——用感知指纹（缩放到 16×16 后哈希）
  比对训练集与评测集图像，命中则剔除，并**在报告中披露剔除数量**。
  若无法执行去污染，**必须在报告中声明「未去污染」**，不能默认干净。

### D4. Video-MME 的抽帧数与磁盘

- **症状**：不同模型分数差异大且不稳定；或磁盘爆满。
- **原因**：抽帧数量显著影响分数；视频本体数百 GB。
- **解法**：四个模型用**同一抽帧策略**；上机先 `df -h`，
  不够就只评 short 子集并如实标注。

## E. 环境与工程

### ⭐ E1. `pip.conf` 指向的内网镜像不可达

- **症状**：`pip install` 卡住或报 `Connection refused` 到 `172.22.x.x`。
- **原因**：`/etc/pip.conf` 配了内网源，但本机不通。
- **解法**：显式指定公网源：
  ```bash
  uv pip install --index-url https://pypi.org/simple <pkg>
  ```

### E2. LLaMA-Factory 与 EasyR1 依赖冲突

- **症状**：装完 EasyR1 后 LLaMA-Factory 报错，或反之。
- **原因**：两者对 `transformers` / `vllm` 的版本要求不同。
- **解法**：**三个独立 venv**（`.venv-lf` / `.venv-rl` / `.venv-eval`），
  **绝不混装**。`env/check_env.py` 会检测同一 venv 内的冲突组合。

### ⭐ E3. HF 仓库改名/迁移（用旧 ID 会 307 跳转或失败）

| 旧 ID（常见写法） | 现状 | 正确 ID |
|---|---|---|
| `HaoyeZhang/RLHF-V-Dataset` | 307 迁移 | `openbmb/RLHF-V-Dataset` |
| `lmms-lab/MME` | 307 迁移 | `lmms-lab-encoder/MME` |
| `lmms-lab/Video-MME` | 307 迁移 | `lmms-eval/Video-MME` |
| `luoruipu1/Valley-Instruct-73k` | 307 迁移 | `luoruipu1/Valley-Instruct-65k` (gated) |
| `LLaMA-Factory` (GitHub) | 301 跳转 | `hiyouga/LlamaFactory` |
| `volcengine/verl` (GitHub) | 301 跳转 | `verl-project/verl` |
| `QwenLM/Qwen2-VL` (GitHub) | 301 跳转 | `QwenLM/Qwen3-VL`（Qwen2-VL 仓库不再维护） |

- **自查**：`curl -sL "https://huggingface.co/api/models/<id>" | python3 -c "import sys,json;print(json.load(sys.stdin)['id'])"`

### E4. 数据集许可陷阱

- **症状**：训练完了才发现数据**禁止商用**。
- **实测**：`ShareGPT4V`、`RLHF-V-Dataset`、`LLaVA-RLHF-Data` 均为
  **CC-BY-NC-4.0（禁商用）**；`LLaVA-Instruct-150K` 为 CC-BY-4.0 但受 OpenAI 条款约束。
- **解法**：**逐个读 dataset card 的 `license` 字段确认，不要靠印象**。
  本项目在 `data/manifests/datasets.yaml` 里逐项标注了许可与风险等级。

### E5. 不要用 `torch.cuda.is_available()` 做环境体检

- **症状**：只想查一下 GPU 情况，结果每张卡被吃掉约 300 MB 显存。
- **原因**：`torch.cuda.is_available()` / 任何 torch CUDA 调用都会
  **创建 CUDA context**，即使什么都不算。
- **解法**：查 GPU 用 `nvidia-smi`；本项目 `env/check_env.py` 默认只走
  nvidia-smi，真实的 torch 检查需要显式加 `--with-cuda`。
