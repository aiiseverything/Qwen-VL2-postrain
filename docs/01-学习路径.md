## 第 1 层：VLM 基础架构（弄懂「模型长什么样」）

**[必读] ViT + Connector + LLM 三段式**
- 读 LLaVA 论文 *Visual Instruction Tuning* 的 §3（架构）与 Figure 1。
- 关键理解：**图像先过 ViT 变成一串 patch 特征，再经 connector 投影到 LLM 的词嵌入空间，
  和文本 token 拼在一起送进 LLM**。之后所有「视觉 token 挤爆显存」的现象都源于此。
- 对照本项目：`Qwen2-VL-2B` 的 ViT + **merger**（把 2×2 patch 合并投影）即 connector。
  配置项 `freeze_vision_tower` = 冻结 ViT，`freeze_multi_modal_projector` = 是否冻结 merger。

**[必读] 为什么冻结 ViT**
- 直觉：ViT 在大规模预训练时已学到通用视觉表征，SFT 数据量相对小，
  全参微调容易把它「训坏」（灾难性遗忘）；冻结还能省显存和算力。
- 本项目：PLAN R6 要求冻结，但 **merger 保持可训练**（D3），让视觉特征适配新指令分布。

## 第 2 层：Qwen2-VL 的两个关键设计（弄懂「为什么它会炸显存」）

**[必读] Naive Dynamic Resolution —— 为什么图像 token 数是变的**
- Qwen2-VL 不做固定尺寸 resize：图像按 28×28 patch 切，**分辨率越高 token 越多**。
- 公式：视觉 token 数 ≈ `(H/28) × (W/28)`。
- **这就是 `image_max_pixels` 存在的原因，也是 OOM 的头号元凶**。
  一张 1024×1024 的图约 1300+ token，是 512×512（约 334）的 4 倍。
- 本项目设 `image_max_pixels: 262144`（=512×512）。**显存不够先降它，不要先降 batch**。
- 源码位置：`transformers` 里 `Qwen2VLImageProcessor` 的 `smart_resize`。

**[必读] M-RoPE（多模态旋转位置编码）—— 为什么它能处理视频**
- 普通 RoPE 只用一维位置；M-RoPE 把位置拆成 **时间 / 高度 / 宽度** 三个分量。
- 好处：图像的空间结构和视频的时序都能被正确编码，且统一了图像与视频的表示。
- 读 Qwen2-VL 技术报告的 M-RoPE 一节。

**[可跳] 为什么 Qwen2-VL 独立仓库不再维护**（已 301 跳到 `QwenLM/Qwen3-VL`）
- 不影响使用，模型权重仍在 `Qwen/Qwen2-VL-2B-Instruct`。

## 第 3 层：SFT（弄懂「loss 该算在谁身上」）

**[必读] loss mask：为什么只在 answer 上算 loss**
- 训练时整段序列都送进去，但 **loss 只对 assistant 的回答计**，
  user 的提问部分被 mask 掉。否则模型会学着「生成问题」而不是「回答问题」。
- 检查方式：LLaMA-Factory 里 `template: qwen2_vl` 定义了角色标签，
  数据格式里 `<image>` 占位符必须出现在 user 侧。

**[必读] 数据格式**
- 本项目统一为 LLaMA-Factory 的 `sharegpt` 多模态格式：
  ```json
  {"messages":[{"role":"user","content":"<image>..."},
               {"role":"assistant","content":"..."}],
   "media":["data/raw/images/coco/train2017/xxx.jpg"]}
  ```
- 见 `scripts/prepare/to_sharegpt.py` 与 `configs/dataset_info.json`。

**[可跳] 数据配比的经验**
- 本项目 40 万条的抽取逻辑与依据写在 `docs/05` 第 4 节，可直接参考。

## 第 4 层：DPO（弄懂「为什么 lr 必须这么小」）

**[必读] 从 RLHF 到 DPO 的推导**
- 读 DPO 论文 *Direct Preference Optimization* 的 §4。
- 核心：RLHF 要训 reward model + PPO，DPO 用**闭式解**把 reward 隐式地
  表达成 policy 与 reference 的对数比，从而**只需一个分类损失**就能直接优化 policy。
- 理解 `pref_beta`：它是 **KL 约束的强度**。beta 越大，policy 越不敢偏离 reference。

**[必读] 为什么 DPO 对学习率极其敏感**
- DPO 的梯度里含 `sigmoid(-beta * (logratio_chosen - logratio_rejected))`，
  尺度与 SFT 完全不同。**用 SFT 的 1e-5 会让 policy 相对 reference 偏移过大，直接训崩。**
- 本项目用 `5e-7`（比 SFT 低 20 倍）。
- 监控指标：`rewards/accuracies` 应在 **0.5–0.8**；迅速冲到 1.0 说明 lr 太大。

**[必读] DPO 需要 policy + reference 两个模型**
- 显存约为 SFT 的 2 倍，这是 batch 只能设 1 的原因。

## 第 5 层：GRPO / RLVR（弄懂「小模型为什么更吃这个」）

**[必读] GRPO 与 PPO 的差别**
- PPO 需要一个 value model 估计 baseline；**GRPO 去掉 value model**，
  改为对同一个 prompt 采样一组（group）回答，用**组内相对优势**做 baseline。
- 好处：省一个模型的内存与训练开销。
- 参数 `worker.rollout.n: 5` = 每个 prompt 采样 5 条。

**[必读] KL 约束的作用**
- `algorithm.kl_coef: 1.0e-2` 防止 policy 为了刷奖励而跑偏（reward hacking）。

**[必读] RLVR：可验证奖励 vs 奖励模型**
- RLVR 不训 reward model，而是用**程序可验证的规则**判分（如答案精确匹配）。
- 为什么小模型更吃 RLVR：奖励信号**无噪声**，不需要 reward model 的泛化能力，
  2B 模型也能稳定优化。

**[必读] 奖励函数是 RLVR 的命门**
- 奖励错了 = 训练白跑，而且**不报错**。
- 本项目 `configs/reward_geo.py` 处理了两种答案格式，并有单测。
- ⚠️ 上机后**第一步**就是看 reward 是否为 0、方差是否为 0。

**[必读] 小模型上强制 CoT 格式奖励会掉分**
- 见 `docs/02` B2。

## 第 6 层：DeepSpeed ZeRO（弄懂「无 NVLink 为什么不能用 ZeRO-3」）

**[必读] Stage 1/2/3 分别分片什么**

| Stage | 分片内容 | 通信量 |
|---|---|---|
| 1 | 优化器状态 | 低 |
| 2 | 优化器状态 + 梯度 | 中 |
| 3 | 优化器状态 + 梯度 + **参数** | 高（每步 all-gather 全参数） |

**[必读] 为什么本项目用 ZeRO-2 而不是 ZeRO-3**
- L40/L20 是 **PCIe 卡，无 NVLink**。ZeRO-3 每个 forward/backward 都要
  all-gather 完整参数，在 PCIe 带宽下成为瓶颈。
- Qwen2-VL-2B 在 ZeRO-2 下显存本来就够（静态约 9.7 GB / 48 GB），
  **没必要付 ZeRO-3 的通信代价**。
- 推导见 `docs/03` 第 8 节。

## 第 7 层：评测方法论（弄懂「分数为什么不可比」）

**[必读] 判分协议决定分数**
- MME 是**是/否**二元题，分数 = accuracy + accuracy+，**对 prompt 模板极度敏感**。
- MathVista 官方用 **GPT 抽取答案**判分；无 key 时用规则抽取，分数**不可与论文比较**。
- Video-MME **抽帧数量**显著影响分数。

**[必读] 为什么必须用同一工具链**
- 四个模型用不同工具评测 → 分差里混着「工具差异」，结论不成立。
- 本项目全部走 VLMEvalKit（PLAN D5）。

**[必读] 数据污染**
- 训练集与评测集图像重叠 → 分数虚高。
- 检测方法：图像感知指纹（缩放 16×16 后哈希）比对。
- 见 `scripts/prepare/quality_filter.py`。
