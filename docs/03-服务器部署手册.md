# 服务器部署手册

> 目标硬件：**4×L40**（PLAN 的原设计目标；卡型差异见第 0 节）
> 目标：从零到跑通 SFT → DPO → GRPO → 评测。

---

## 0. 先读这一段：本项目的环境背景

PLAN 写的是「Mac 开发 + 4×L40 训练」的双机分工。**实际勘查结果与此不符**，
动手前请先确认你手上的机器到底是哪种：

| | PLAN 的假设 | 本次实际勘查到的工作机 |
|---|---|---|
| 机型 | MacBook Air (Apple Silicon) | Linux x86_64 |
| GPU | 本机无 GPU | **7× NVIDIA L20 (46 GB)** |
| CUDA | — | 13.0 (driver 580.126.16) |
| 磁盘 | 306 GB 可用 | 9.0 TB 可用 (`/home/ml-user/workdir`) |

**关键差异**：如果你打算在**有 GPU 的机器上跑训练**，那么本文的
「4 卡」需要按实际卡数调整（`NPROC` 与 `n_gpus_per_node`）。

> ⚠️ **重要**：本项目的训练配置**没有经过任何真实多卡运行验证**。
> 配置是按 PLAN §8 写的、做了结构级检查，但从未在 GPU 上跑过。
> 请务必按第 5 节的「吞吐校准」先跑 100 step。

## 2. 三套独立环境（规避 PLAN 风险 K2）

⚠️ **这是硬性要求**：LLaMA-Factory 与 EasyR1 对 `transformers`/`vllm`
的版本要求冲突，**装在一起会互相破坏**。

| venv | 用途 | 安装脚本 | requirements |
|---|---|---|---|
| `.venv-lf` | SFT + DPO | `env/server_l40_sft.sh` | `env/requirements-server-sft.txt` |
| `.venv-rl` | GRPO (EasyR1/verl) | `env/server_l40_rl.sh` | `env/requirements-server-rl.txt` |
| `.venv-eval` | 评测 (VLMEvalKit) | `env/server_l40_eval.sh` | `env/requirements-server-eval.txt` |

```bash
export PROJECT_ROOT=/home/ml-user/workdir/project-2
bash env/server_l40_sft.sh
bash env/server_l40_rl.sh
bash env/server_l40_eval.sh

# 逐个自检
python3 env/check_env.py --stage sft
python3 env/check_env.py --stage rl
python3 env/check_env.py --stage eval
```

### 2.1 内网镜像不可达（本项目实测）

`/etc/pip.conf` 可能指向不可达的内网源。所有安装命令**显式指定公网源**：

```bash
uv pip install --python .venv-lf/bin/python --index-url https://pypi.org/simple <pkg>
```

### 2.2 离线/弱网环境

若目标机器网络差，可在**本机**先用 uv 把 wheel 缓存下来再拷过去：

```bash
# 有网机器
uv pip download --python .venv-lf/bin/python -r env/requirements-server-sft.txt -d wheels/
# 目标机器
uv pip install --python .venv-lf/bin/python --no-index --find-links wheels/ -r env/requirements-server-sft.txt
```

## 5. 训练

### 5.1 ★ 先做吞吐校准（PLAN Phase 7.4）

**不要直接放全量。** 先跑 100 step 测吞吐与显存：

```bash
cd $PROJECT_ROOT
NPROC=4 bash scripts/train/launch_4xl40.sh sft --max_steps 100
```

看三件事：
1. **显存峰值**：`nvidia-smi` 观察。若离 48 GB 还很远，可以调大 batch。
2. **每 step 耗时** → 外推总时长 = `总样本次 / global_batch × step 耗时`。
3. **loss 曲线**：SFT 应平滑下降；若震荡或 NaN，降 lr。

据实测结果调整 `configs/sft_qwen2vl_2b.yaml` 的
`per_device_train_batch_size` / `gradient_accumulation_steps`。

### 5.2 三个阶段

```bash
# SFT (2 epoch, 冻结 ViT, ZeRO-2)
NPROC=4 bash scripts/train/launch_4xl40.sh sft

# DPO (基于 SFT ckpt, 1 epoch)
NPROC=4 bash scripts/train/launch_4xl40.sh dpo

# GRPO (200 step)
NPROC=4 bash scripts/train/launch_4xl40.sh grpo
```

**断点续训**：`launch_4xl40.sh` 会自动探测输出目录下最新的
`checkpoint-*` 并追加 `--resume_from_checkpoint`，直接重跑同一命令即可。

### 5.3 GRPO 特别提示（风险 K3）

EasyR1 的 `examples/` 下**只有 Qwen2.5-VL / Qwen3-VL 的脚本，没有 Qwen2-VL 的**。
`configs/grpo_qwen2vl_2b.yaml` 是从 `qwen2_5_vl_3b_geo3k_grpo.sh` 改写的，
属于「官方支持但未被重点验证」的路径。

**建议的上机顺序**：
1. 先用 `data/processed/rlvr/geometry3k.parquet`（2,101 条，EasyR1 官方示例数据）
   跑 10 step，确认管线通。
2. 再换 `geoqa_r1v.parquet`（8,031 条）跑全量 200 step。
3. 若 Qwen2-VL 路径报错难以排查，**降级方案**：先用 Qwen2.5-VL-3B 跑通
   完整 GRPO 管线验证配置逻辑，再换回 2B。

**训练开始后立刻检查 reward**：
- 若 reward **恒为 0** → 奖励函数/答案列有问题（见 `docs/02` B1）
- 若 reward 方差为 0 → 所有 rollout 得分相同，GRPO 无法产生优势信号
- 若 `rewards/accuracies` 迅速冲到 1.0 → 任务太简单或数据泄漏

## 6. 评测

```bash
# 12 次评测 = 4 个模型 (pretrained / SFT / DPO / GRPO) × 3 个 benchmark
bash scripts/eval/run_all.sh

# 汇总成对比表
```

### 6.1 评测纪律（否则结论不可信）

- **四个模型必须用同一工具链、同一 prompt 模板、同一抽帧策略**（PLAN D5）
- MathVista 无 OpenAI key 时用规则判分 → **报告中必须标注「非官方判分」**（K6）
- Video-MME 视频数百 GB，先 `df -h`；不够就只评 short 子集并标注（K7）
- 若 SFT 未含视频数据，**Video-MME 预期不涨甚至下降**，这是诚实发现而非失败

## 7. 常见报错对照表

| 报错 | 原因 | 解法 |
|---|---|---|
| `CUDA out of memory`（调小 batch 仍 OOM） | 视觉 token 过多 | 降 `image_max_pixels`（见 `docs/02` C1） |
| reward 恒为 0 | 答案列名/格式不匹配 | 查 `docs/02` B1；先跑奖励函数单测 |
| `train_batch_size does not match` | DeepSpeed batch 配置 | 保持 `"auto"` |
| NCCL timeout / hang | 卡被占 / 端口 / IB | 见 `docs/02` C4 排查顺序 |
| `Connection refused` 到 `172.22.x.x` | 内网 pip 源不可达 | `--index-url https://pypi.org/simple` |
| `KeyError: 'answer'`（geoqa） | 该数据集用 `solution` 列 | 见 `docs/02` B1 |
| `unzip: bad CRC` | 跨源续传损坏 | 删掉重下；用 `unzip -t` 预校验 |
| `hf download` 卡住不传 | Xet 后端静默卡死 | `uv pip uninstall hf_xet` |
| 找不到 vLLM/transformers 版本 | venv 混装 | 三个 venv 分开（K2） |
| DPO 后模型输出崩坏 | lr 太大 | DPO lr 降到 5e-7（`docs/02` C2） |

## 8. 显存估算（PLAN §8.1 的推导，供你上机前判断）

**SFT，单卡，ZeRO-2，冻结 ViT 后可训练参数 ≈ 1.5B**

| 项 | 计算 | 占用 |
|---|---|---|
| 参数 bf16（全模型，ZeRO-2 不分片参数） | 2.21B × 2 B | ~4.4 GB |
| 梯度 bf16（仅可训练，4 卡分片） | 1.5B × 2 / 4 | ~0.8 GB |
| 优化器 AdamW fp32（4 卡分片） | 1.5B × 12 / 4 | ~4.5 GB |
| **静态小计** | | **≈ 9.7 GB** |
| 激活值（开 gradient_checkpointing） | 随 batch 与**视觉 token 数**变化 | 余量约 38 GB |

> 结论：48 GB 卡上**非常充裕**，`per_device_train_batch_size` 很可能还能上调 ——
> 这正是要在第 5.1 节实测的原因。

**DPO**：需同时载入 policy + reference 两个模型，静态占用约为 SFT 的 **2 倍**
（≈15 GB），48 GB 仍够用，但激活余量减半，故 batch 设得保守
（`per_device_train_batch_size: 1`）。
