## 0. 一句话结论

PLAN 的**执行策略是可行的，但它的环境事实和下载策略都不成立**：它描述的是
「一台无 GPU 的 MacBook + 一台 4×L40 服务器」，而实际只有**一台 7×L20 的 Linux 机器，
且 7 张卡全部被占用**；它假设的数据集「下载即得图像」，而实际上
**三个 SFT 数据源全都只有标注 JSON，没有任何图像或视频本体**。

这些不是小偏差 —— 如果照着 PLAN 直接执行，第一步下载就会全部失败。
下文逐条记录**我怎么发现的、怎么处理的、以及还留下什么风险**。

## 2. 问题清单（按发现顺序）

### 🔴 P1 — 三个 SFT 数据源**只有标注，没有图像/视频**（最严重）

**发现方式**：拉取 HF 仓库文件清单后发现
`LLaVA-Instruct-150K` 只有 5 个 `.json`；`ShareGPT4V` 只有 4 个 `.json`；
`VideoInstruct-100K` 只有 1 个 `VideoInstruct100K.json`。**一张图、一个视频都没有。**

**这是最致命的偏差**：PLAN §7.1 写「LLaVA-665K 全量图像 ~100 GB」，
读起来像是从该仓库下载图像，但该仓库根本不提供图像。

**处理**：逐一确定上游来源并核实可达性，新增了 PLAN 中不存在的下载步骤
（`scripts/download/01b_images.sh`）：

| 标注里的前缀 | 实测条数 (LLaVA-665K) | 上游图像来源 | 本机可达性 |
|---|---|---|---|
| `coco/` | 364,100 | COCO train2017 (19.34 GB) | ✅ 经 HF 镜像 |
| `vg/` | 86,417 | VisualGenome VG_100K/100K_2 | ⚠️ 官方站不可达，走 HF 镜像 |
| `ocr_vqa/` | 80,000 | OCR-VQA (~250 GB) | ❌ **成本过高，整组剔除** |
| `gqa/` | 72,140 | GQA images (21.82 GB) | ✅ 经 HF 镜像 |
| `textvqa/` | 21,953 | TextVQA (7.07 GB) | ✅ 原始站可达 |

### 🔴 P2 — VideoInstruct 的 `video_id` 是 **YouTube ID**

**发现方式**：`VideoInstruct100K.json` 的字段是 `{q, a, video_id}`，
`video_id` 形如 `v_k_ZXmr8pmrs` —— 这是 ActivityNet 的命名约定，`v_` 后面是 YouTube 视频 ID。

**含义**：视频必须用 `yt-dlp` 从 YouTube 抓取，**不是**从 HF 下载。
YouTube 抓取存在下架、地区封锁、限流等不确定性，且本机 YouTube 可达性实测为
HTTP 200（3.99s），但**批量抓取 1.3 万个视频的稳定性无法预先保证**。

**好消息**：10 万条 turn 只对应 **13,303 个唯一视频**，按视频去重后抓取即可覆盖，
工作量比「10 万条」的直觉小一个数量级。

### 🟠 P3 — 学术原始站点的下载速度**不可用**

**发现方式**：首次按 PLAN 直连原始站点，实测速率异常：

| 站点 | 实测速率 | 下载 19–22 GB 预计耗时 |
|---|---|---|
| `images.cocodataset.org` (COCO) | **0.05 MB/s** | ≈ 107 小时 |
| `downloads.cs.stanford.edu` (GQA) | **0.03 MB/s** | ≈ 198 小时 |
| `dl.fbaipublicfiles.com` (TextVQA) | 1.49 MB/s | ≈ 79 分钟（可接受） |

**处理**：改用 HF 镜像并做了 30–50 MB 区间实测对比：

| 源 | 速率 | 相对提速 |
|---|---|---|
| HF `pcuenq/coco-2017-mirror` | **4.15 MB/s** | **83×** |
| HF `Feeky929/GQA-images` | **3.40 MB/s** | **113×** |
| `visualgenome.org` | **连接失败 (curl code 000)** | 完全不可达 |

> ⚠️ 另一个隐含教训：PLAN §2.2 记录「huggingface.co 可直连，无需镜像」是在
> **另一台机器**上测的。同一域名在不同网络位置的表现可以差两个数量级，
> **任何网络结论都必须在本机重测**。

### 🟠 P4 — 我用 `pkill -f` 把自己的 shell 杀掉了

**现象**：执行 `pkill -f "01b_images.sh"` 后，命令以 **exit code 144** 结束，无输出。

**原因**：`pkill -f` 匹配的是**完整命令行**，而执行该命令的 shell 自身
命令行里就包含 `01b_images.sh` 这个字符串 —— 于是它把自己也匹配并杀掉了。

**后果**：该次调用中，`pkill` 之后的所有清理指令（包括 `rm`）**都没有执行**，
导致第一轮「慢速下载」的 curl 进程存活下来，与第二轮重启的下载**写同一个文件**
（`gqa_images.zip`、`textvqa_images.zip` 各有两个写入者），产生了竞态。

**处理**：
1. 改为**按 PID 精确 kill**（`ps -eo pid,args` 取 PID，再 `kill -9`）。
2. 在 `_common.sh` 中加入 `record_pid` / `stop_by_pidfile`，并把这条教训写进注释。
3. 清空被竞态污染的目录，重新干净下载。

### 🟠 P5 — 跨源续传可能产生损坏文件

**现象**：GQA 的 `images.zip` 曾从**慢速的 Stanford 源**下到 9.6 MB，
换到 **HF 镜像**后 `curl -C -` 直接从 9.6 MB 处续传。

**风险**：`curl -C -` 只做字节偏移续传，**不校验前序字节是否来自同一个文件**。
若两个源的同一路径文件内容不同，续传结果就是拼接出来的损坏文件 ——
而这种损坏**不会在下载时报错**，只会在几小时后的解压阶段才暴露。

**处理**：删除该 partial 重新下载（代价是几秒，而非几小时）；
在 `_common.sh` 中新增 `verify_zip()`，解压前对每个归档做 `unzip -t` 完整性校验。

### 🔴 P6 — RLVR 答案格式不统一，会导致奖励**恒为 0 且不报错**

**发现方式**：读取真实 parquet 后发现两个数据集的答案列**既不同名、也不同格式**：

| 数据集 | 答案列名 | 值样例 |
|---|---|---|
| `hiyouga/geometry3k` | `answer` | `3` （裸答案） |
| `leonardPKU/GEOQA_R1V_Train_8K` | **`solution`** | `<answer> 145° </answer>` （带标签） |
| `FanqingM/MMK12` | `answer` | 裸答案 |

**为什么危险**：这是**静默失败**。
- 若按 `answer` 列取 geoqa 的答案 → 该列不存在，8,031 条全部拿到空标签；
- 若用朴素的字符串相等比较 `145°` 与 `<answer> 145° </answer>` → 永不相等。

两种情况下 GRPO 的奖励都是**恒 0**，训练照常跑完 200 step，
loss 曲线看起来「正常收敛」，但实际上模型什么都没学到。

**处理**：`configs/reward_geo.py` 先剥离 `<answer>/<solution>/<think>` 标签，
再做「规整化精确匹配 → 数值容差匹配 → 子串包含」三级比较，
并写了一个 7 条用例的单元测试覆盖两种格式（全部通过）。

### 🟠 P7 — `images` 字段是 `numpy.ndarray`，误判会导致整组数据被静默丢弃

**现象**：`build_rlvr.py` 首次运行输出 `geometry3k: 0 行`。

**原因**：我最初只判断 `isinstance(cell, (list, tuple))` 来取多图列表的第一个元素，
但 pyarrow 读出的 `list<struct>` 实际是 **`numpy.ndarray`** —— 既不是 list 也不是 tuple，
于是被判定为「无图」，**2,101 条几何训练数据被全部静默丢弃**。

**处理**：改为「非 dict 即视为可索引序列」，并加注释说明这个坑。
修复后 geometry3k 正常产出 2,101 行。

### 🟡 P8 — DPO 图像以 bytes 内嵌，需落盘成文件

**现象**：RLHF-V 的 `image` 字段是 `struct<bytes, path>`，图像二进制直接躺在 parquet 里。

**处理**：`build_dpo_pairs.py` 把图像按内容 hash 命名落盘到
`data/processed/dpo_images/`，再让 jsonl 的 `images` 字段指向真实文件路径 ——
LLaMA-Factory 读 DPO sharegpt 格式时要求 `images` 指向**真实存在的文件**。

### 🟡 P9 — `RLHF-V-Dataset` 的许可是 CC-BY-NC-4.0，不是 Apache-2.0

**现象**：我按印象在清单里先写了 `Apache-2.0`，读 dataset card 后发现是
**`cc-by-nc-4.0`（禁止商用）**。

**处理**：立刻更正清单，并把它从「low risk」提到 **HIGH**。
现在 `HIGH` 风险（禁商用）的共 3 项：ShareGPT4V、RLHF-V、LLaVA-RLHF。

> 教训：**许可必须逐个读 dataset card 确认，不能靠印象填。**

### 🟡 P10 — RLHF-V 下载中途停滞（0.00 MB/s）

**现象**：`hf download` 的进程还活着，但 `.incomplete` 文件字节数长时间不变，
同期其余三个流正常（5.5 / 3.9 / 1.0 MB/s）。

**处理**：终止该进程，保留 partial，加 `HF_HUB_DISABLE_XET=1` 关闭 Xet 传输后重启。
> Xet 是 HF 的新传输后端，在部分网络下会静默卡住而**不报错、不超时** ——
> 表现为「进程活着但不传输」。遇到这种症状优先试这个开关。

### 🟡 P11 — LLaVA-665K 里有 40,688 条**不是视觉数据**

**发现方式**：统计 `image` 字段缺失时发现 40,688 条没有该键，
键集合是 `('conversations','id','model')` —— 内容是 Java 编程问答、中文法律咨询等
**纯文本 ShareGPT 对话**（占 665,298 条的 6.1%）。

**处理**：在抽取阶段显式剔除并计入统计（见 `docs/05` 第 4 节与 `stats_report.md`），
避免它们混进 VLM 的 SFT 数据。

### 🟡 P12 — LLaVA-mix665k 与 ShareGPT4V-mix665k 高度重叠

**发现方式**：两个文件的图像前缀分布几乎一致
（coco 364,100 vs 349,860；vg/gqa/textvqa 条数完全相同；同为 665K 量级）。

**含义**：ShareGPT4V 的 `mix665k` 是**在 LLaVA-665K 基础上改写的**，不是独立数据集。
若按 PLAN §7.1 的「LLaVA 235K + ShareGPT4V 65K」直接相加，
会有大量**同图重复**（同一张 COCO 图出现在两边）。

**处理**：改用 ShareGPT4V 的 `cap100k`（GPT-4V 生成的 caption，内容独立），
并只取其中 `coco`+`llava` 两组以复用已下载的 COCO 图像（见第 4 节）。

### 🟡 P13 — `pip.conf` 指向的内网镜像不可达

**现象**：`/etc/pip.conf` 的 index-url 是 `http://172.22.1.36/pypi/simple/`。

**处理**：`project-1/baseline/setup_env.sh` 里已有同款记录（「内部 pip 镜像在本机不可达」）。
本次一律显式 `--index-url https://pypi.org/simple`，不使用该内网源。

### 🔴 P14 — 视频 ID 前缀没剥，导致「所有视频都不可用」的假象

**现象**：首次跑视频探测，**12 个视频 0 个可用**，全部返回
`This video is unavailable`。看起来像是整个视频数据集已经失效。

**原因**：`VideoInstruct100K.json` 的 `video_id` 形如 `v_k_ZXmr8pmrs`。
`v_` 只是 **ActivityNet 的标记前缀**，真正的 YouTube ID 是 `v_` **之后**的部分。
把整个字符串拼进 URL（`watch?v=v_k_ZXmr8pmrs`）会得到一个不存在的 ID，
YouTube 对不存在与已下架的 ID 返回同样的 `unavailable`，因此**完全看不出是拼错了**。

**处理**：`fetch_videos.py` 增加 `youtube_id()` 剥掉 `v_` 前缀，并加注释说明。

**效果**：同样 20 个抽样，剥离后 **16 个可用（80%）** —— 0% → 80%。
失败 4 个的真实构成：下架 2 / 私享 1 / 超时 1。

> 教训：**「全部失败」通常指向系统性错误（拼写/前缀/权限），而不是数据本身失效。**
> 遇到 100% 失败率时，先怀疑自己的请求构造，再怀疑数据。

### 🟡 P15 — `LLaVA-RLHF-Data` 不含显式的 chosen/rejected

**现象**：按 PLAN §7.2 取该数据集补足 DPO 到 1 万条，但读出的字段是
`{id, image, conversations, captions[], caption_type, length_bonus}` ——
**没有 chosen/rejected**。`captions` 只是多个候选回答的并列列表，
README 也没有给出任何排序约定。

**风险**：若凭空假设「第一条最好」来造偏好对，会**污染 DPO 的偏好信号**。
DPO 对错误偏好标签极其敏感 —— 标签反了，模型会朝反方向优化。

**处理**：**默认不从这里造对**。`build_dpo_pairs.py` 加
`--allow-llava-rlhf-heuristic` 开关（默认关闭），只有显式开启时才用
`length_bonus`/长度的启发式推导，并在输出里加 `assumption` 字段标记，
便于日后审计。当前 DPO 产出为 **RLHF-V 的 5,731 对**，缺口 4,269 对，
原因与三个备选方案已写入 `HANDOFF.md` 第 3.1 节。

### 🔴 P16 — yt-dlp 默认客户端把「仍然存在」的视频报成不可用（险丢 5,000 个视频）

**现象**：13,303 个视频探测下来，**7,157 个（54%）** 状态为 `error`，
报错 `This video is not available`。看着像大半个数据集已经失效。

**原因**：yt-dlp 默认的 `web` 客户端在本网络下，对大量**实际可以播放**的视频
也返回 `This video is not available`。这个报错字面上和「视频已删除」几乎一样，
**无法从输出区分**，所以极易被当成数据失效而直接放弃。

**处理**：改用 `--extractor-args youtube:player_client=android,web`。

**效果（实测，同一批视频）**：

| | 通过 <3 分钟 | 覆盖 turn 数 |
|---|---|---|
| 修复前 | 2,864 / 13,303（21.5%） | 22,120 |
| 修复后 | **7,739 / 13,303（58.2%）** | **58,809** |

`error` 类从 7,157 降到 540 —— 救回约 5,000 个视频，可用数据 **2.7 倍**。

> 教训：**不要只看错误字符串的字面意思就下结论。**
> 抽 10 个「失败」样本换个方式重试，成本几分钟，收益是 2.7 倍的数据量。

### 🟠 P17 — `unzip -t` 对大型 ZIP64 归档会**误报损坏**

**现象**：21.8 GB 的 GQA 归档用 `unzip -t` 校验时报
`not enough memory for bomb detection` 和 `bad zipfile offset`，
看起来像损坏；但用 Python `zipfile` 读，条目数、文件内容都正常。

**原因**：系统自带的老 `unzip` 对 **ZIP64**（>4 GB 或 >65535 成员的归档）
支持和内存策略都有问题，会把正常归档判成「压缩炸弹」而拒绝处理。

**处理**：完整性校验改用 Python `zipfile`——
`scripts/download/01c_extract_images.py` 会抽查若干成员做**真实读取**，
读得出来才算完好。这比 `unzip -t` 既准确又可诊断（能报出具体成员和异常类型）。

### 🔴 P18 — 数据流水线的依赖顺序排错，关键路径被非关键任务堵死

**现象**：初次无人值守跑了一夜，早上发现流水线卡在「视频下载」，
后面的 SFT 抽取 / 去污染 / 统计**全部没执行**。

**原因**：我把「视频下载」排在了 SFT 抽取**之前**，而视频有 7,739 个要下
（按当时速率约 18 小时）。但视频只占 SFT 数据的一部分，
**图像侧的数据准备根本不需要等它**。

**处理**：拆成两条**互不阻塞**的轨：
- `scripts/run_pipeline.sh` —— 图像轨（关键路径）：等图像 → 解压 → 抽取 → 去污染 → 统计
- `scripts/run_video_pipeline.sh` —— 视频轨（独立）：探测 → 下载 → 回填视频样本 → 重新去污染

> 教训：**排流水线前先问「谁真的依赖谁」**，而不是按「数据来源的编号顺序」排。
> 一条链上只要有一个长任务排在关键路径前面，整条链就被它决定。

### 🔴 P19 — 我自己的判重 bug 导致 GQA 归档被写坏（本次最贵的一课）

**现象**：无人值守跑完后，`unzip -t` 报 GQA 归档损坏。进一步查：
文件 **22.04 GB，比预期的 21.82 GB 大 221 MB**；
zipfile 能读出 148,855 个条目，但每个成员都 `Bad magic number for file header`。

**原因**：我在修 `resume_all.sh` 的判重逻辑**之前**，它的条件写错了字段
（拿 `$3`（文件名）去比 `$script`，而 `ps -eo args` 下完整路径在 `$2`），
这个条件**永远为假**，于是判重失效、**启了两个 `curl -C -` 同时写同一个文件**。
两个 curl 各自按自己记录的偏移 seek+write，交错写入 ——
结果就是文件变大、内部偏移全部错乱。

**处理**：删除损坏文件重新下载（单写入者），修复后大小 **字节级精确匹配** 21,817,965,542。

**但真正的教训不是那行写错**，而是：

> **我修好判重之后，只验证了「不再有重复进程」，没有回头验证
> 「在 bug 窗口期内已经写完的文件是否还完好」。**
> 修复一个数据损坏类的 bug 时，**必须同时重新校验该 bug 影响期内产出的所有文件**。

**幸好**：解压前的 `verify_zip` 守卫生效，损坏文件**没有流进训练**。
这也说明「下载后立刻做完整性校验」这条规则的价值 —— 它把一个可能污染整个
训练结果的静默故障，变成了一个会在解压阶段大声报错的显性故障。

## 2.2 训练框架搭建阶段的问题（Phase 3 实况）

### 🔴 P20 — `torchrun` 命中了别的 venv，报错完全指不到真因

**现象**：多卡启动失败，子进程报
`ModuleNotFoundError: No module named 'transformers'`（换成 `llamafactory` 也一样）。
单卡跑得好好的，一上多卡就崩。

**排查过程**（走了两步弯路）：
1. 先怀疑 editable 安装没生效 → 单独测 `import llamafactory` **成功**，
   说明不是包的问题。
2. 加上 `PYTHONPATH` 后，报错从 `No module named 'llamafactory'`
   **变成了** `No module named 'transformers'` —— 这个「错误换了个名字」
   才是关键线索：说明子进程**根本是另一个 Python 在跑**。

**根因**：LLaMA-Factory 的 launcher 是用 `torchrun`（**靠 PATH 解析**）拉起子进程的。
本机 PATH 上先命中 `/opt/venv/main/bin/torchrun`，它的 shebang 指向
`/opt/venv/main/bin/python3`（Python 3.10，没有装 transformers）。
而我们自己的 venv 在 `PATH` 里根本没出现。

**处理**：把 venv 的 bin 放到 PATH 最前面：
```bash
export PATH="$VENV/bin:$PATH"
```
已写入 `scripts/train/launch_4xl40.sh`。

> 教训：**多环境共存时，任何「子进程报缺包」的问题，第一步先确认
> 子进程用的到底是哪个 Python。** 症状（缺 transformers）和病因（torchrun 来自
> 另一个 venv）之间隔着一层 PATH 解析，很容易往错的方向查。

### 🟠 P21 — 多模态数据集里图像字节的列名**各不相同**

**现象**：去污染脚本报告 `MathVista 收集 0 张评测图像指纹`，
即对 MathVista 的去污染**实际没生效**，但脚本不会报错。

**原因**：各 benchmark 存图像的方式不统一（实测）：

| 数据集 | 图像字节实际在哪 | 另有 |
|---|---|---|
| MME | `image` = `struct<bytes, path>` | — |
| MathVista | **`decoded_image`** = `struct<bytes,…>` | `image` 只是**路径字符串** `"images/1001.jpg"` |

原代码只找 `image` / `images` 两列，在 MathVista 上取到的是字符串而非字节，
于是静默地贡献 0 个指纹。

**处理**：`_cell_to_bytes()` 支持 bytes / dict / ndarray 三种形态；
候选列改为 `("decoded_image", "image", "images")` 并**逐列探测确认含字节**；
同时在输出里显式标注「未取到字节 —— 该 benchmark 的去污染未生效」，
让「没生效」这件事**可见**，而不是伪装成「检查通过」。

**修复效果**：MathVista 指纹数 0 → **6,141**。

> 教训：**「检查跑了」不等于「检查生效了」。**
> 任何过滤/校验步骤都应该输出「实际处理了多少条」，
> 否则 0 条也会静悄悄地和成功长得一模一样。

### 🟡 P22 — 依赖版本冲突：LlamaFactory 与 PLAN 的钉版要求不一致

**现象**：装 LlamaFactory 时解析失败 —— 它要求 `transformers>=4.55.0`，
而 PLAN/EasyR1 钉的是 `4.54.0`。

**处理**：
- LlamaFactory 主分支（v1 rewrite）实际按 **transformers 5.x** 开发，
  在 4.56.2 上会因 `HfArgumentParser` 类型解析更严格而崩
  （`Type resolution failed for ... TrainingArguments`）。
- 最终选定 **LlamaFactory v0.9.5 + transformers 4.55.4 + torch 2.6.0**：
  这是能满足双方约束、且经过验证的组合。
- 本机另装了 `torchaudio`（LlamaFactory 的多模态插件会 import 它，
  缺了直接在 import 期就崩）。

> 这条印证了 PLAN 风险 K2 的判断：**框架之间的依赖冲突是真实存在的**，
> 三个独立 venv 是硬性要求。

### 🔴 P23 — 视频样本塞进 `images` 列，报错完全指不到视频

**现象**：`ValueError: The number of images does not match the number of
<image> tokens in [{'role':'user','content':'<video>\nCan you describe...'}]`

**原因**：我最初把所有媒体的列名统一叫 `media`，并在 `dataset_info.json` 里
映射成 `images`。但 LLaMA-Factory 对图像和视频用**两个不同的列**：
`images` 对应内容里的 `<image>`，`videos` 对应 `<video>`。
视频样本进了 `images` 列 → 数量对不上 → 报错。

**处理**：`to_sharegpt.py` 按 `media_type` 拆成 `images` / `videos` 两列；
`dataset_info.json` 同时映射两列。

> 注意报错信息里**完全没提视频**，只说「images 数量不匹配」。
> 如果不去看内容里的 `<video>` 标记，很容易误判成图像数据的问题。

### 🔴 P24 — `cutoff_len` 按 PLAN 设 2048 太小，长样本直接炸

**现象**：`RuntimeError: shape mismatch: value tensor of shape [3, 3375]
cannot be broadcast to indexing result of shape [3, 2048]`

**原因**：PLAN §8.1 设 `cutoff_len: 2048`，是按「图 ~334 token」估的。
但实测 LLaVA 有 **9,774 字符 ≈ 3,258 token 的长对话**，加上图像 token
远超 2048。截断发生在文本侧，而**图像 token 不会被截**，于是数量对不上。

**处理**：`cutoff_len: 2048 → 4096`（三个 SFT/DPO 配置同步改），
并把质量过滤的字符阈值设为 11,000（≈3,667 token，为视觉 token 留余量）。

> 教训：PLAN 里的超参是**基于假设估的**，不是实测的。
> `cutoff_len` 这类参数必须拿真实数据的最长样本验证一遍。

### 🔴 P25 — `video_maxlen` 默认 128 帧，是 PLAN 里完全没提的隐藏地雷

**现象**：把 `cutoff_len` 提到 4096 后**仍然**报 shape mismatch：
`value tensor of shape [3, 5391] cannot be broadcast to [3, 4096]`。
溢出量几乎不变（~1,300 token），说明视觉 token 才是真凶。

**原因**：LLaMA-Factory 的 `video_maxlen` **默认 128 帧**。
按 `video_fps: 2.0` 采样，128 帧 × 每帧约 20 token ≈ **2,560 视觉 token**，
一个视频样本就能把 4096 的窗口撑爆。

**处理**：显式设 `video_maxlen: 32`（≈640 token）。

> 这是本次最隐蔽的一个坑：**PLAN 完全没提这个参数**，它是框架的内部默认值。
> 只要数据集里混了视频样本，不显式设置就会炸，而报错只显示 shape mismatch。

### 🟠 P26 — 我又一次让同一个脚本跑了多个实例（判重失效复发）

**现象**：发现**三个** `quality_filter.py` 进程同时往
`data/processed/sft_400k.clean.jsonl` 写入。

**原因**：`/tmp/filter.sh` 被启动了三次（两次修复后重跑、一次正式跑），
而我此前用于清理的 `for p in $(ps ... | awk ...)` 循环**没有真正杀掉**旧进程，
于是新的叠加在旧的之上。

**处理**：按 PID 逐个确认并 kill，删除被污染的输出文件，重新只跑一个实例，
并在启动后**显式核对"正在运行的实例数 == 1"**。

> 这是 P4/P5/P19 同一类问题的第三次出现：
> **「启动一个写文件的长时间任务」时，必须验证「当前只有一个写入者」。**
> 这次的代价只是重跑 2 小时；如果没发现，产出的训练数据会是静默损坏的。

### 🔴 P27 — 过滤规则把 4.7 万条**合法单选题答案**当垃圾删了

**现象**：质量过滤输出 352,349 条，比输入少了 **47,367 条**，
其中 `dropped_empty_answer` 占 47,289。

**排查**：把被丢的样本捞出来看，答案全是 `'A'` / `'B'` / `'C'` / `'D'` ——
**是 VQA 单选题的正常答案**。

**原因**：我的规则写成 `if len(ans.strip()) < 2: drop`。
「长度 < 2」的初衷是过滤空答案/噪声，但**单选题的答案天然就是单字符**。

**影响**：**12% 的训练数据被静默删除**。而且这个 bug 不会报错，
只会让最终条数少一点 —— 如果不是我顺手核对了一下丢弃明细，根本发现不了。

**处理**：改为只丢**真正为空**的答案（`not ans.strip()`）。
修复后：输出 **399,573** 条，只丢 143 条（全部是去污染命中的）。

> 教训：**任何"丢弃数据"的规则，都必须输出"丢了多少、为什么"并且被人工核对。**
> 一个静默多丢 12% 数据的过滤器，比一个直接报错的过滤器危险得多。

### 🟠 P28 — 同一个路径 bug 只修了一半（SFT 修了，DPO 漏了）

**现象**：核对 DPO 数据时发现 `images` 字段是**相对路径**
（`data/processed/dpo_images/xxx.png`）。

**影响**：LLaMA-Factory 解析 sharegpt 的 `images` 字段时是相对
**数据集文件所在目录** 的。于是路径会被拼成
`data/processed/` + `data/processed/dpo_images/xxx.png`
= `data/processed/data/processed/dpo_images/xxx.png` —— **不存在**。
DPO 一跑就会失败（或静默丢图）。

**原因**：我在 SFT 侧（`to_sharegpt.py`）改用绝对路径时，
**没有回头检查同样写路径的 `build_dpo_pairs.py`**。两处代码独立，
改了一处就以为改完了。

**处理**：`build_dpo_pairs.py` 也改为返回 `p.resolve()`，重新生成并逐条校验
（5,731 条，路径问题 0）。

> 教训：**修一个模式化的 bug 时，要主动搜一遍"同样的写法还出现在哪里"。**
> 同源 bug 往往不止一处，只修被发现的那一处，剩下的会在几个阶段之后才爆。

### 🔴 P32 — `launch_4xl40.sh` 的参数传递是坏的（含断点续训）

**现象**：`launch_4xl40.sh sft --max_steps 100` →
`ValueError: Some keys are not used by the HfArgumentParser: ['--max_steps', '100']`

**真因**：LLaMA-Factory 在 config 是 `.yaml` 时，用
**`OmegaConf.from_cli(sys.argv[2:])`** 解析额外参数 —— 这是 **`key=value` 点列表语法**，
不是 argparse 的 `--key value`。

**影响被低估的地方**：脚本里的断点续训也是用 `--resume_from_checkpoint` 传的，
**所以一个 20 小时任务的中断恢复路径本身就是坏的** —— 这个 bug 平时看不出来，
只有在训练崩了要续跑时才致命。

**修法**：加 `normalize_overrides()`，把 `--k v` / `--k=v` / `k=v` 三种形式
统一翻译成 `key=value`；续训改用 `resume_from_checkpoint=<path>`。

### 🔴 P33 — 评测数据源被误判为"不可达"（其实是 HTTPS 被阻断）

**现象**：VLMEvalKit 的 MME / MathVista 标注托管在
`opencompass.openxlab.space`，HTTPS 连续 **0/10 全部失败**（`curl` 返回 000），
一度判定为「数据源不可达，需要自己造替代 TSV」。

**真因**：**只有 HTTPS 被阻断，HTTP 完全正常**。实测：

| 方式 | 结果 |
|---|---|
| `https://opencompass.openxlab.space/...` | **0/10 失败** |
| `http://opencompass.openxlab.space/...` | **200** ✅ |
| 走 IP + HTTPS | 200（说明不是 IP 层封禁） |

**修法**：用 HTTP 一次性取回两个**官方** TSV：

| 文件 | 大小 | md5 与 VLMEvalKit 期望值 |
|---|---|---|
| `MME.tsv` | 48 MB | `b36b43c3f09801f5d368627fb92187c3` ✅ **完全一致** |
| `MathVista_MINI.tsv` | 55 MB | `f199b98e178e5a2a20e7048f5dcb0464` ✅ **完全一致** |

放在 `$LMUData/` 下后，`prepare_tsv` 检测到 md5 匹配会**跳过下载** ——
所以**不需要修改 VLMEvalKit 的任何 URL**，避免了把整个库的下载降级成 HTTP。

> 教训：**「不可达」要先分层验证**（DNS / TCP / TLS / 应用层），
> 我差点因为只测了 HTTPS 就去手搓替代数据集 —— 那会引入无法与论文对比的分数。

### VideoMME 的接线（用户要求：只评测 3 分钟以内）

Video-MME 的 900 个视频分 short(<2min) / medium / long 各 300，
官方仓库打包成 20 个 ~5GB 的 zip（~101 GB）且**不按时长分包**。

**做法**：
1. 用 **HTTP Range 请求**读远端 zip 的中央目录，**只下载需要的文件**
   （`scripts/download/05_videomme_short.py`）—— 补齐 300 个 short 视频只用了 **3.09 GB**
2. 给 VLMEvalKit 打了**两个小而明确的补丁**（都在代码里注明 `[Postrain 补丁]`）：
   - `VLMEVALKIT_VMME_DURATION=short` 环境变量，按时长筛选题目
   - 启用该变量时跳过 md5 校验（因为本地 TSV 是**有意**过滤过的子集）
3. 用**符号链接**搭建 HF 缓存布局，避免复制 73 GB

**验证**（离线，不触网）：
```
✅ VideoMME 数据集构建成功
   题目数: 900      唯一视频: 300
   video_path: ./video/fFjv93ACGo8.mp4
```

> ⚠️ **分数口径**：筛选后的 900 题是 **short 子集分数**，
> **不可与官方全量 2700 题的分数直接比较**。四个模型用同一子集，横向可比。

### 🔴 P34 — yt-dlp 格式选择器写得太窄，白白丢掉一半视频

**现象**：视频轨跑完，7,739 个通过时长筛选的视频**只下到 3,772 个（约 49%）**，
另外 3,910 个状态为 `error`。

**误判**：一开始以为是「视频已下架 / 被 YouTube 限流」，准备接受这个成功率。

**真因**：实际报错是
```
ERROR: Requested format is not available. Use --list-formats ...
```
**不是视频不可用，是我要求的格式组合不存在。** 原选择器是：

```
bv*[height<=480][ext=mp4]+ba[ext=m4a] / b[height<=480][ext=mp4] / b[height<=480]
                      ^^^^^^^^            ^^^^^^^^
              硬要求视频是 mp4, 音频是 m4a
```

而 YouTube 上大量视频**只提供 webm/opus 轨**，凑不出 mp4+m4a 组合，于是直接判失败。
**这些视频其实完全正常** —— 探测阶段能取到时长就是证据。

**处理**：选择器放宽为多级回退，容器统一交给 `--merge-output-format mp4`：
```
bv*[height<=480]+ba / b[height<=480] / bv*+ba/b / best
```

**效果**：对同批"失败"视频抽样，修复前 **0/3** → 修复后 **3/3 成功**。
全量重下实测错误率 **从 ~50% 降到 0.3%**（1,950 个里仅 5 个失败）。

> 教训：**「格式不可用」和「内容不可用」是两回事。**
> `Requested format is not available` 说的是**我的请求**有问题；
> `Video unavailable` 才是**内容**有问题。
> 差一个词，代价是一半的数据集 —— 而我差点把它当成数据源限制接受了。

### 🔴 P35 — LLaMA-Factory 会**静默续训**旧 checkpoint，换卡数就炸

**现象**：7 卡训练链跑到校准阶段，21 分钟后失败：

```
ZeRORuntimeException: The checkpoint being loaded used a DP world size of 3
but the current world size is 7. Automatic adjustment of ZeRO's optimizer state
partitioning with a new world size is not currently supported.
```

**真因**：`configs/calib_sft_b4.yaml` 的 `output_dir` 是 `results/calib/sft_b4`，
里面**留着 9-22 那次 3 卡校准的 `checkpoint-20`**。
LLaMA-Factory 在 `hparams/parser.py:486-499` 有这段逻辑：

```python
if (training_args.resume_from_checkpoint is None
        and training_args.do_train
        and os.path.isdir(training_args.output_dir)
        and not overwrite_output_dir
        and can_resume_from_checkpoint):
    last_checkpoint = get_last_checkpoint(training_args.output_dir)
    if last_checkpoint is not None:
        training_args.resume_from_checkpoint = last_checkpoint   # ← 静默生效
```

**即：只要 `output_dir` 存在且里面有 checkpoint，它就自动续训**，只在 INFO 级
打一行 "Resuming training from ..."。我配置里没写 `resume_from_checkpoint`，
所以完全没往这个方向想。

**为什么换卡数会炸**：ZeRO-2 的优化器状态是**按 DP world size 分片**的。
3 卡存的每片大小与 7 卡要求的完全不同，DeepSpeed **不支持自动重新分片**。

**处理**：
1. 删掉陈旧的 `results/calib/`（33 GB）
2. 给校准配置加 `overwrite_output_dir: true`（校准本就是丢弃式的，不该续训）
3. 全量 SFT 的 `results/checkpoints/` 已确认为空，不会误触发

> 教训：**框架的「便利」特性（自动续训）在换硬件配置时会变成陷阱。**
> 而且它是**静默**的 —— 只在 INFO 日志里提一句。任何「上次的产物会影响这次运行」
> 的行为，都应该在启动前显式确认，而不是假设它只在你想续训时才生效。

### 🔴 P36 — 训练死在「容器 host 内存」，不是显存（连续踩了 3 次）

**现象**：全量 SFT 跑到 step 27 被杀，训练日志里**没有任何 CUDA OOM**（显存峰值才
34–40 GB / 46 GB），只有一行：

```
exitcode: -9 (SIGKILL) received by PID 1230805      # rank 0
22:02:20  进度条打到 step 27（此后 12 分半**零输出**，在 thrash）
22:14:46  被杀
```

**真因**：**容器 cgroup 内存上限只有 64 GiB，而宿主机有 503 GB** ——
`free -g` 看到的是宿主机那 503 G，这是第一个把人带偏的地方。判定要看：

```bash
cat /sys/fs/cgroup/memory.max        # 65536 MB  ← 真正的天花板
cat /sys/fs/cgroup/memory.events     # oom_kill 1 ; max 1370950  ← 137 万次贴着上限回收
```

7 个 rank × `dataloader_num_workers: 8` = **56 个 worker 进程**。worker fork 后
COW 被逐步私有化，**匿名内存以 ~95–180 MB/s 单调上涨**（实测 `pt_data_worker`
平均 RSS 3.4 GB），18 分钟填满 64 GiB。

**为什么能撑过前面 4 小时 tokenize**：tokenize 只读那个 538 MB 的 jsonl，
**完全不碰图像**；图像/视频是在 dataloader worker **构造 batch 时**才解码的。
所以内存压力从训练开始那一刻才出现，而且 worker 私有内存是**逐渐**膨胀的 ——
这解释了"为什么不是第 0 步就死"。

**处理**：`dataloader_num_workers: 8 → 1`（56 → 7 个 worker）。漂移治好，
基线 **35 GB 平台期**。代价：10.4 → 12.9 s/it，慢约 15–25%。

> 教训：**先看 cgroup，再看 `free`。** 另外 worker 数不只是吞吐旋钮，
> 它是 **host 内存的乘数** —— 调 batch size（影响显存）对这里毫无帮助。

### 🔴 P37 — 每存一次 checkpoint 永久吃掉 ~25 GB，而且**不归还**

**现象**：worker 降到 1、漂移治好之后，训练在 **step 200 的第二次保存**时又死。
监视进程每 60 秒采样的轨迹把因果拍得很清楚：

```
step  95   anon=35.2 G                       ← 保存前，稳定（漂移已平台）
step 100   anon=54.5 G   TOTAL=58.8G         ← 保存！+19.3 GB
step 140   anon=55.0 G                       ← 25 分钟后仍卡在 55 G，**没有归还**
step 165   anon=55.5 G   TOTAL=62.3G         ← 基线已吃掉几乎全部余量
step 200   第二次保存 → 58.8+19 = 73 G > 64 G → SIGKILL rank 0
```

存的是什么：`checkpoint-100/global_step100/` 实测 **23 GB** ——
7 个 rank 各 ~3.3 G 的 `bf16_zero_pp_rank_N_mp_rank_00_optim_states.pt`
（= fp32 master 6.3 G + Adam 的 m/v 12.6 G + bf16 模型 4.4 G）+ 4.6 G 的
`model.safetensors`。

**为什么"存磁盘"要占主机内存**：能写进 `write()` 的只有主机内存里的字节 ——
optimizer state 在**显存**里，必须先 **GPU → CPU 拷一份**（本机没有 GPUDirect
Storage）；序列化又是**异步**的（DeepSpeed 的 checkpoint 引擎），源缓冲得活到写完。
实测 **`anon` 涨 +19 G 而 `file`（页缓存）全程稳在 5–6 G 没动** ⇒ 是**进程内的张量
缓冲区**，不是内核脏页。而且 **7 个 rank 全都在物化**（文件其实只需 rank 0 写）。

**试过但无效**：

| 尝试 | 结果 |
|---|---|
| `MALLOC_ARENA_MAX=1` + `MALLOC_TRIM_THRESHOLD_` + `MALLOC_MMAP_THRESHOLD_` | **无效**（3 次保存实测 `27.9 → 53.9 → 52~53 卡住 → 57 G`）⇒ **不是 glibc 分配器碎片** |
| `save_only_model: true`（只写 4.6 G 模型） | **无效**：日志 0 次 DS optimizer 保存，anon **照样 +20 G**（`29.3 → 49.6 G`）⇒ 尖峰**不跟写入字节数成正比** |

**处理**：`save_steps: 100000`（大于总步数 4758）—— **中途一次都不存**。
收尾时 LLaMA-Factory 会**无条件**调 `trainer.save_model()`
（`third_party/LlamaFactory/src/llamafactory/train/sft/workflow.py:121-122`），
只存模型（~+20 G，落在 35 G 基线上 = 55 G，能活），
`results/checkpoints/sft/model.safetensors` **照样产出**，DPO 阶段不受影响。

**代价（如实记录）**：中途崩 = **没有任何存档可续，17 小时全丢**。
**更优解**：把容器上限从 64 GiB 调到 128 GiB（宿主机有 503 G）——
即可用回 `worker=8` + 正常 `save_steps`，13 小时跑完，训练协议零妥协。

> 教训：**"存到磁盘"不等于不占内存。** 写出去的字节必须先经过主机内存，
> 而且这份内存**不保证还回来** —— 一次保存把基线从 35 G 抬到 55 G 之后，
> 下一次保存就是要命的那次。

### 🔴 P38 — 用短跑验证内存行为，会被"跑通一次"骗过去

### 🔴 P41 — LLaMA-Factory 视频解码**不关容器**，每个视频泄漏 2.6 MB（OOM 的第二个机制）

**现象**：把 `dataloader_num_workers` 降到 1、漂移治好了、也不存 checkpoint 了，
但训练内存**仍在涨**：按进程归因发现 **7 个 `pt_data_worker` 各自以 ~12 MB/min
线性增长**（7 个共 ~84 MB/min），推算 4 小时后又撞 64 GiB —— 一个 17 小时的
训练根本跑不到头。

```
02:13  anon=37.6G  step=80
02:36  anon=39.2G  step=185
02:54  anon=41.0G  step=260      ← 线性，没有平台期
7 个 pt_data_worker: 4.1–5.7 GB each 共 36.1 GB（还在涨）
7 个 rank 进程:      2.5–4.0 GB each 共 25.3 GB（稳定）
```

**真因**：`third_party/LlamaFactory/src/llamafactory/data/mm_plugin.py` 的
`Qwen2VLPlugin._regularize_videos`（`qwen2_vl` 模板的视频路径，训练时 collator
每遇一个视频样本就走这里）：

```python
else:
    container = av.open(video, "r")          # ← 开了
    ...
    for frame_idx, frame in enumerate(container.decode(video_stream)):
        if frame_idx in sample_indices:
            frames.append(frame.to_image())
    ...                                       # ← 从头到尾没有 container.close()
```

同类的兄弟函数 `_get_qwen_video_stream_metadata` 是**有** `container.close()` 的
（line 2037），只有这条训练路径漏了。

**为什么难发现**：**只有真正解码视频才会涨**。所以 4 小时的 tokenize 阶段
（只读 jsonl、不碰图像）完全正常，纯图像样本也不明显 —— 只有训练跑起来、
视频样本不断流过 collator 才暴露。而且它**慢**（84 MB/min），短跑几分钟看不出来。

**实测**（40 个真实视频，复刻解码模式，脚本 `scripts/training/leak_test_plugin_paths.py`（video 模式））：

| 变体 | 40 个视频后 RSS | 每视频增长 | 推算每优化步 |
|---|---|---|---|
| 原代码 | 219.4 MB（+183.4） | **+2.61 MB** | ~+59 MB |
| 加 `container.close()` | 124.2 MB（第 20 个后**完全走平**） | **+0.04 MB** | ~+1 MB |

**处理**：把解码块包进 `try/finally`，`finally` 里 `container.close()`
（用 try/finally 是因为坏视频会抛 `ValueError`，那条路径也必须释放）。
`Qwen3VLPlugin` / `GLM4VPlugin` / `Qwen2OmniPlugin` 都继承它，一并受益。

**上线验证**（2026-09-27 03:53–03:57 实跑，`scripts/training/check_private_memory.py`）：

```
T0 03:53:32  rank 私有 9.17G   worker 私有 9.66G   cgroup anon 28.20G   step 122
T1 03:57:34  rank 私有 9.19G   worker 私有 9.70G   cgroup anon 28.24G   step 140
             (+0.02G / 18 步)                    (+0.04G)   ← 等于噪声
```

修复前是 **+100 MB/min**（一轮必死），修复后 **+0.01 GB/min = 噪声级**。
离线对照（直接调真实类，`scripts/training/leak_test_plugin_paths.py`）：视频 60 条 RSS 760→731 MB（不涨）、
图像 100 条 705→705 MB（不涨）。

修复后 worker 的 **RSS 仍在涨（+18 MB/min）**，一度让人以为补丁没生效 ——
其实那是 **mmap 的 tokenized 数据集页（file-backed 共享页）** 被逐步 touch，
它不占匿名内存、内核可随时回收、也不会撞爆 cgroup。
**判据要用 `/proc/<pid>/smaps_rollup` 的 `Private_Dirty`**（或 cgroup 的 `anon`），

> ⚠️ **补丁存在 `env/patches/llamafactory-video-decode-leak.patch`** ——
> 因为 `third_party/` 在 `.gitignore` 里，改动不进主仓库，重克隆就会静默丢失。
> 应用方式见 `env/patches/README.md`。

> 教训：**框架的"别人的代码"也要按进程量内存**。这次是靠"按进程归因"才定位到
> worker（`results/watch/procs.log`）—— 只看容器总量只能知道"涨了"，
> 知道"是谁涨的"才能顺着找到 `av.open`。
> **而且这次是"降 worker 数治好一个泄漏、又暴露出另一个"** —— 治好了症状
> 不等于没有下一个。

### 🔴 P42 — CUDA OOM：离群长样本 × logits 的 fp32 上采样，撑爆单卡显存

**现象**：修好 host 内存泄漏后（anon 全程平稳 28–29 GB ✓），训练跑到
**step 1016（3 小时 50 分）** 又挂了 —— 但这次是**显存**：

```
[rank3]: torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 13.44 GiB.
GPU 3 has a total capacity of 44.39 GiB of which 5.86 GiB is free.
Including non-PyTorch memory, this process has 38.52 GiB memory in use.
Of the allocated memory 37.81 GiB is allocated by PyTorch,
and 172.16 MiB is reserved by PyTorch but unallocated.
```

**先排除碎片**：`reserved but unallocated` 只有 **172 MiB** —— 不是碎片
（PyTorch 那句 `expandable_segments:True` 的建议在这里不适用），
是**真实需求超了容量**：38.52 + 13.44 = 52 GiB > 44.39 GiB。

**13.44 GiB 是什么**：`ForCausalLMLoss` 第一行就是 `logits = logits.float()`
（为了数值稳定把 logits 升到 fp32 再算交叉熵）：

```
batch 8 × 序列长 × 词表 152064 × 4 字节
  = 8 × ~2960 × 152064 × 4 ≈ 13.4 GiB   ✓ 与报错数字完全对上
```

**为什么会有 2960 token 的 batch**（实测全部 399,593 条的真实长度，
`scripts/training/measure_seq_len.py`）：

| 均值 | p50 | p90 | p95 | p99 | p100 |
|---|---|---|---|---|---|
| 537 | 497 | 759 | 819 | 958 | **4096** |

随机 batch=8 的"batch 内最长"均值只有 **796**（fp32 logits 3.6 GiB，完全正常）——
但只要**混进一条几千 token 的离群长样本，padding 会把它拉满整批 8 条**
→ 8 × 2960 → 13.4 GiB → 必死。最坏情况（批内有 4096 token）需 18.6 GiB，
总需求 ~52 GiB ❌。**这是结构性缺陷，不是运气**：跑 1016 步才撞上只是概率。

**为什么之前没发现**：配置注释里的"显存峰值 34 GB / 46 GB，0 次 OOM"来自
**1024 条样本的校准跑** —— 小样本校准根本覆盖不到全量数据的长度长尾。
**校准能验证流程，验证不了尾部分布。**

**处理**：`per_device_train_batch_size: 8 → 2`，
`gradient_accumulation_steps: 3 → 12`。

* global batch 仍是 **2 × 12 × 7 = 168** ⇒ **训练协议零改变**
* batch 2 的最坏情况：fp32 logits 仅 4.6 GiB ⇒ 总需求 ~37 GiB ✓ 余量 7 GiB
* 为什么不用 batch 4：最坏情况 9.3 GiB ⇒ 总需求 ~45 GiB，贴着 44.39 GiB 上限 ⚠️（会复发）
* **为什么 batch 2 不吃亏**：微 batch 越小，"batch 内最长"越短
  （8 条 796 vs 2 条 ~650 token），同样 168 样本的 padding 总量反而**少 ~18%**
* 两个字段都在 HF `TrainingArguments` 里 ⇒ **不会**让 4 小时 tokenize 缓存失效（见 P39）

**实测效果**：显存峰值 **44.0 GB → 15.5–18.0 GB**（余量 0.4 GB → 26 GB），
`s/it` 15.23 → 15.47（无明显变化）。

> 教训：**小样本校准验证不了长尾**。以及：**OOM 报错里的
> "reserved but unallocated" 是判断碎片 vs 真实需求超限的关键数字** ——
> 它很小就说明不是碎片，别照着 PyTorch 的建议去调 allocator。
> 判"是什么撑爆的"要用**算术对上号**（13.44 GiB = 8 × 2960 × 152064 × 4）。

## 4. 「40 万条怎么抽」的决策（用户授权由我决定）

**配额**

| 来源 | 条数 | 图像来源 |
|---|---|---|
| LLaVA-665K | 220,000 | COCO / GQA / TextVQA / VG |
| ShareGPT4V `cap100k` | 80,000 | COCO（取 coco+llava 两组） |
| VideoInstruct-100K | 100,000 | YouTube（仅时长 < 3 分钟） |
| **合计** | **400,000** | |

**四条依据**

1. **只选图像真能拿到的来源。** 可用池 = coco 364,100 + gqa 72,140 + vg 86,417 +
   textvqa 21,953 = **544,610 条**。ocr_vqa 的 80,000 条上游约 250 GB 且需逐图匹配，
   成本远超收益，整组剔除；40,688 条纯文本对话不属于视觉数据，一并剔除。
2. **LLaVA 配额按可用池比例分层抽样**，让四个图像来源都被覆盖，
   而不是被占比 67% 的 coco 一家淹没。
3. **ShareGPT4V 只取 coco+llava 两组**，复用 COCO 图像，
   避免为 `sam/wikiart/web-*` 等 21,998 条再下 ShareGPT4V 自建图像包。
4. **视频占 100,000**，与图像形成模态互补 —— 这正是 PLAN D6 想保住
   Video-MME 评测轴意义的做法，且比 PLAN 原配额（35K）更能支撑视频能力。

> ⚠️ 抽取脚本会自动跳过图像缺失的样本并计入统计，
> 因此**首次产出的实际条数可能低于 400,000**，缺口与原因会在
> `data/manifests/stats_report.md` 中如实列出。

## 附录 A：核实方法

- 硬件与进程：`nvidia-smi --query-gpu/--query-compute-apps`、`ps -eo pid,args`、`df -h`、`free -g`
- 网络：`curl -o /dev/null -w "%{http_code} %{time_total}"`；
  速率对比用 `curl -r 0-52428799` 区间下载 + 计时
- HF 仓库：`https://huggingface.co/api/{models,datasets}/<id>?full=true` 取
  `siblings` 文件清单、`gated`、`downloads`
- 数据集 schema：`pyarrow.parquet.read_schema` + `pandas.read_parquet` 实读首行
- 归档大小：`curl -sIL` 读 `Content-Length`

> 本文所有数字均为**本机实测**，未使用记忆或推测值。
> 凡未能核实的（如视频抓取成功率、训练耗时）均标注为未完成/待测，不提供估计值冒充事实。
