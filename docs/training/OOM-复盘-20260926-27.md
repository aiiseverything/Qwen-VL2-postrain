## 0. 先记住三条环境事实

| | 值 | 怎么确认的 |
|---|---|---|
| **容器内存上限** | `65536 MB = 64 GiB`，平台固定 | `cat /sys/fs/cgroup/memory.max` |
| **宿主机内存** | `503 GB` | `free -g` |
| **无 swap** | `memory.swap.max = 0` | 所以匿名内存一旦涨上去只能靠进程自己释放 |

**这三条是全部分析的地基**：容器只有 64 GiB，而宿主机有 503 GB ——
任何"机器内存够大"的直觉都是错的。所有 OOM 都是**容器级**的，
和显存无关（全程 **0 次 CUDA OOM**，显存峰值 34–40 GB / 46 GB）。

另外两条判定依据：

```bash
# 内核杀的，不是 CUDA
#   训练日志里: exitcode: -9 (SIGKILL) received by PID ...
#   cgroup: memory.events = oom_kill 1 ; max 1370950   ← 137 万次贴着上限回收
```

## 2. Case 1：worker=8，死在 step 27

### 现场

```
17:09:26  第一次手动起 SFT（tokenize 阶段）
17:39:46  正式训练链启动（run_chain.sh）→ 校准通过
17:46:48  链的 SFT 启动
17:47:42  Loading dataset
17:47→21:55  【静默 4 小时 08 分】tokenize（16 个 worker，无日志输出）
21:55:41  tokenize 缓存写完（16/16 分片，3.5 GB）
21:56:11  ***** Running training *****  Num examples = 399,593
22:02:20  进度条打到 step 27（此后 12 分半**零输出**）
22:14:46  SIGKILL rank 0 (pid 1230805)
22:14:58  链判定 ❌ SFT 失败 后 exit 1 → DPO/GRPO/评测 一步都没跑
```

### 根因（诊断实验 #1 复现，`logs/diag/sft_memtest.log`）

用**完全相同的配置**跑 `max_steps=25`，内存轨迹：

```
22:34:48  TOTAL= 6.8G  ANON= 4.0G   python 10 个
22:35:38  TOTAL=16.2G  ANON= 8.1G   ← 加载数据集
22:35:59  TOTAL=52.6G  ANON=45.9G   ← 7 个 rank 各涨到 ~6.9GB（DeepSpeed 初始化）
22:36:09  TOTAL=41.1G  ANON=33.2G   python 52 个（worker 被 fork）
22:36:50  TOTAL=57.4G  ANON=46.2G
22:38:22  TOTAL=65.5G  ANON=54.9G   ← 顶到 65536MB，FILE 从 10.1G 被挤到 8.9G
```

* 56 个 `pt_data_worker`，**平均 RSS 3.4 GB**（`ps` 汇总 186.8 GB，是共享页口径）
* 崩溃时 7 个 rank 各 ~6.3–7.0 GB
* 增长速率 ~95–180 MB/s —— 18 分钟内填满 64 GiB

**为什么能撑过 4 小时 tokenize 却死在训练第 27 步**：tokenize 只读那个 538 MB 的
jsonl，**不碰图像**；图像/视频是在 dataloader worker **构造 batch 时才解码**的
（LLaMA-Factory 的 collator 此时才把路径变成像素）。所以内存压力从训练开始那一刻
才出现，而且 worker 的私有内存是**逐渐**膨胀的 —— 解释了"为什么不是第 0 步就死"。

## 4. Case 3：worker=1，死在 step 200（最关键的一次）

把 worker 从 8 降到 1 之后，漂移治好了（基线 35 GB 就平台期），
但**第二次保存还是要了命**。监视进程 `scripts/train/watch_train.py`
每 60 秒采一次样，完整记录了"只涨不退"：

```
step  95   anon=35.2 G   TOTAL=42.9G      ← 保存前，稳定（漂移已平台）
step 100   anon=54.5 G   TOTAL=58.8G      ← 保存！+19.3 GB
step 105   anon=54.7 G                    ← 保存结束
step 140   anon=55.0 G                    ← 25 分钟后仍卡在 55 G，**没有归还**
...
step 165   anon=55.5 G   TOTAL=62.3G      ← 基线已吃掉几乎全部余量
step 200   第二次保存 → 58.8+19 = 73 G > 64 G
00:02:35   SIGKILL rank 0
```

### 存的是什么

`results/checkpoints/sft/checkpoint-100/`（存活的那份）实测：

```
global_step100/                                 23 G   ← DeepSpeed 分片状态
  bf16_zero_pp_rank_{0..6}_mp_rank_00_optim_states.pt   7 个 rank 各 ~3.3 G
  mp_rank_00_model_states.pt
model.safetensors                              4.6 G   ← bf16 权重
```

23 G 恰好等于 **fp32 master weights 6.3 G + Adam 的 m/v 12.6 G + bf16 模型 4.4 G**
≈ 23.3 G。**每个 rank 只持有自己那 1/7 的分片，但保存时要在主机内存里凑出自己那份**。

### 为什么要用主机内存（常被误解的点）

"存磁盘为什么要占内存" —— 因为**能写进 `write()` 的只有主机内存里的字节**：

1. **数据在显存里**。optimizer state 分片在 7 张卡上，写文件前必须 **GPU → CPU 拷一份**
   （本机没有 GPUDirect Storage，DMA 直写磁盘那条路走不通）。
2. **序列化不是零拷贝**。`torch.save`/`safetensors` 要遍历 state_dict、拼 header、
   逐张量导出字节；而且写是**异步**的（日志里 `[Torch] Checkpoint ... about to be
   saved!` → `ready now!` 来自 DeepSpeed 的异步 checkpoint 引擎），源缓冲区必须
   活到后台线程写完。
3. **实测证明是 1+2，不是内核页缓存**：`anon` 涨了 +19~20 G，而 `file`（页缓存）
   全程稳在 5–6 G 没动。所以不是"写文件的脏页占内存"，而是**进程内的张量缓冲区**。
4. **7 个 rank 全都在构造**。文件其实只有 rank 0 需要写（`model.safetensors` 只写一份），
   但实测 7 个 rank 都各涨了一份 —— 保存路径没有按 rank 收窄，7 份拷贝白占 ~20 G。

### 按进程归因（`results/watch/procs.log` 同类采样）

| 进程 | 保存前 | 保存后 | 涨幅 |
|---|---|---|---|
| rank (3 个) | 3.1–4.2 G | 6.6–7.3 G | **+3.1 ~ +3.7 G** |
| rank (4 个) | 2.5–4.1 G | 3.4–5.1 G | +0.8 ~ +1.0 G |
| 7 个 `pt_data_worker` | 2.5–3.9 G | 不变 | **0** |

dataloader worker **一点没动** —— 尖峰完全来自 rank 进程（保存路径）。

## 5. 排除项：试过但**无效**的

| 尝试 | 结果 | 证据 |
|---|---|---|
| `dataloader_num_workers: 8 → 2` | 漂移速率从 ~180 降到 ~35 MB/s，**但基线仍会撞顶**；保存尖峰不变 | 诊断 #3 |
| `dataloader_num_workers: 2 → 1` | 漂移治好（基线 35 G 平台期），**但保存尖峰仍在** | 诊断 #4 + Case 3 |
| `MALLOC_ARENA_MAX=1`、`MALLOC_TRIM_THRESHOLD_=131072`、`MALLOC_MMAP_THRESHOLD_=33554432` | **完全无效**。3 次保存实测 anon `27.9 → 53.9 → 52~53（卡住）→ 57 G` ⇒ **不是 glibc 分配器碎片** | 对照实验（`logs/diag/ratchet.log`，已清理） |
| `save_only_model: true` | **无效**。日志 0 次 DeepSpeed optimizer 保存、只写了 4.6 G 的 `model.safetensors`，但 anon **照样 +20 G**（`29.3 → 49.6 G`）⇒ 尖峰**不跟写入字节数成正比** | 对照实验（`logs/diag/ratchet2.log`，已清理） |
| `tokenized_path`（让数据集走 mmap 省匿名内存） | **反效果**：它落在 `data_args` 里，会改变 datasets 的 map 指纹 → **4 小时 tokenize 缓存失效**，白跑一次 | 诊断 #2 |
| 降低 `per_device_train_batch_size` | 与 host 内存无关（batch 影响的是**显存**激活值；本项目显存有富余） | — |
| `free -g` 显示宿主机 503 G | **是宿主机不是容器**，容器上限 64 GiB。别被骗 | — |

### 附带发现：tokenize 缓存的指纹规则（重要）

`datasets` 的 map 指纹 = `dill.dumps(transform) + 输入数据集指纹`，而 transform 是
**绑定方法** `dataset_processor.preprocess_dataset` —— `dill` 会把整个处理器实例
（含**全部 `data_args`**）序列化进去。

> ⇒ **任何 `data_args` 字段变动都会让 4 小时的 tokenize 缓存失效**
> （`preprocessing_num_workers` / `cutoff_len` / `image_max_pixels` / `video_maxlen` /
> `tokenized_path` / `dataset` … 改一个就要重跑 4 小时）
>
> ⇒ 而 `dataloader_num_workers` 在 HF 的 `Seq2SeqTrainingArguments` 里，
> **不在 `data_args`**（LLaMA-Factory 的 `hparams/` 无此字段，processor 也不持有
> `training_args`），所以**调它不影响缓存**。

缓存本体：`cache/hf/datasets/json/default-3d379ea0a8bd3d7f/.../cache-b29e49275b12fcb0_000{00..15}_of_00016.arrow`（16 分片，3.5 GB）。

判定方法：配置一致时 2 分 04 秒就进训练（命中）；只多了 `tokenized_path` 就从头 tokenize。

## 6. 64 GiB 上限下的账

| 场景 | 基线 | 一次保存后 | 结论 |
|---|---|---|---|
| worker=8，训练中漂移 | 涨到 65 G+ | — | **保存前就死** |
| worker=2 | 47 G 且仍在爬 | 47+20 = 67 G | 死 |
| worker=1 | **35 G（平台期）** | 35+19~26 = **55~61 G** | **第 1 次保存能活** |
| worker=1 + 第 2 次保存 | 55 G | 55+19 = 74 G | **必死** |

⇒ **任何中途保存都会永久抬高基线，从而毒死最后一次保存。**
所以中途**一次都不能存**，连 `save_only_model` 那种小保存也不行（实测照样 +20 G）。

## 7. 最终采用的配置与理由

```yaml
dataloader_num_workers: 1     # 8 -> 1：治训练中的漂移（代价 10.4 -> 12.9 s/it，约慢 15-25%）
save_steps: 100000            # 故意大于总步数 4758 ⇒ **不存周期 checkpoint**
```

**外加一个源码补丁**（不是配置能解决的，见 §5.1）：
`env/patches/llamafactory-video-decode-leak.patch` → `Qwen2VLPlugin._regularize_videos`
补上 `container.close()`。**这是把 17 小时跑完的前提** —— 不补的话，worker 会以
84 MB/min 线性涨满，4 小时左右必死。

**收尾时模型照样会存**：LLaMA-Factory 在 `train()` 之后**无条件**调用
`trainer.save_model()`（`third_party/LlamaFactory/src/llamafactory/train/sft/workflow.py:121-122`），
只存模型权重（~+20 G，落在 35 G 基线上 = 55 G，能活），产出
`results/checkpoints/sft/model.safetensors` —— DPO 阶段的 `model_name_or_path` 就是它。

**代价（明确记录，不粉饰）**：中途崩溃**没有任何存档可续**，17 小时全丢。
这是 64 GiB 上限下的取舍，不是最优解。

**更优解（需平台配合）**：把容器内存上限从 64 GiB 调到 128 GiB。
宿主机有 503 GB。调完可以用 `worker=8` + 正常 `save_steps`，13 小时跑完（10 s/it），
训练协议零妥协。

## 8. 悬而未决 / 未验证

1. **"保存后内存不归还"的确切代码路径没钉死**。已排除 glibc 碎片；
   目前最像 DeepSpeed 异步 checkpoint 引擎（`deepspeed/runtime/checkpoint_engine/`）
   或 HF Trainer 的 state_dict 缓存**仍持有引用**，且下次保存再叠一份。
   要证实需读这两处源码（都在仓库/venv 里可查）。**若证实，则可能有一个
   代码级修复（保存后显式释放 + 只让 rank 0 物化），能把尖峰从 26 G 降到 ~5 G。**
2. ~~worker=1 的漂移是否真的会平台期~~ → **已定性，是第五个机制**（2026-09-27 结案）：
   它**不会**平台期，是**线性泄漏**。按进程归因定位到 7 个 `pt_data_worker`
   各自 ~12 MB/min；顺着找到 `Qwen2VLPlugin._regularize_videos` 里
   `av.open()` 解码视频后**从不 `container.close()`**，每个视频泄漏 ~2.6 MB。
   已打补丁（`env/patches/llamafactory-video-decode-leak.patch`），
   实测 2.61 → 0.04 MB/视频。**详细见 `docs/05` P41。**
   ⚠️ 补丁的**效果尚未在真实训练里长跑验证**（只有 40 个视频的离线对照实验）。
   重启后前 1 小时要看 `results/watch/procs.log`：worker 的 RSS 应当走平。
3. **DPO 阶段**：`save_steps: 200` 而总步数只有 91（5731 样本 ÷ 63 global batch），
   天然不会中途保存 ⇒ 预估安全，但**未实测**。
4. **GRPO 阶段（verl）**：`save_freq: 50`、`save_model_only: false`，会保存完整状态。
   verl/FSDP 的内存行为与 DeepSpeed 完全不同（还有 vLLM 的显存/固定内存），
   **未测**。到这个阶段前应重新评估（考虑 `save_model_only: true` 或调大 `save_freq`）。

## 10. 教训清单（给未来的自己）

1. **容器内存上限和宿主机内存是两件事** —— 先看 `/sys/fs/cgroup/memory.max`，
   别看 `free -g`。
2. **host 内存 OOM 在日志里只留一行 SIGKILL**，必须**主动采样**才能发现。
   本次能定位，全靠 `scripts/train/watch_train.py` 每 60 秒记的内存轨迹。
3. **别用短跑验证长跑的内存行为**。诊断 #4 只跑 14 步、只存 1 次，看到
   "保存后 54 G，活下来了"就以为没问题 —— 而真凶是"保存**不归还**"，
   需要**至少两次保存**才暴露。**验证内存要看至少两次同类事件。**
4. **改 `data_args` 之前先想 tokenize 缓存**（4 小时）。改
   `dataloader_num_workers` 是安全的（在 training_args 里）。
5. **诊断日志别删**。本次两次对照实验（malloc 参数、`save_only_model`）的原始
   日志在重启前被清理了，只剩本文抄录的数字。
6. **`save_only_model` 不等于"小保存"** —— 实测照样 +20 G。
